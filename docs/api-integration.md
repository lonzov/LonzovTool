# 接口集成约束

前端侧接入后端时必须遵守的约束。后端实现位于独立私有仓库，其内部设计不在本文件描述。

接口契约正文在**后端私有仓库**（`docs/api.md`），本仓库不复制。本文件只讲前端怎么用、以及哪些坑只在特定入口暴露。

## 一、后端是增强，不是依赖

**Cloudflare 免费版对大陆的访问是薛定谔状态**——部分地区在高峰期会连接慢、
带宽小甚至完全连不上。Service Worker 缓存整站产物就是为解决这个问题而引入的：
壳子与静态资源留在本地，回源链路不可用时站点照常打开。

因此这是一条硬约束，不是一般性的"优雅降级"：**已经能打开的站点，绝不能被接口拖垮。**
若核心数据只能来自接口，CF 抖动时用户连一个能打开的页面都拿不到，
等于把 SW 的价值全部还回去。

- **静态产物必须自包含**：接口全部不可用时，站点仍完整可用，只是数据停在构建期快照。
- 所有消费接口的前端逻辑一律沿用「取不到就用兜底值」的写法
  （参考 `useStats.js`、`DownloadTool.vue` 的 catch 分支），
  **不得把接口失败升级成页面错误态或路由跳转**。
- 爬虫与首屏拿到的是构建期内联的快照，运行时再通过接口刷新为最新数据。
- 唯一的例外是"已被淘汰"这一类失败（`410` + `code: endpoint_retired`，
  或版本比对发现自己代次低于 `min_supported`）：它证明当前客户端跑的是过期代码，
  兜底之外还要**触发一次更新检查并提示**（复用 `useSWUpdate` 与更新弹窗）。
  **不得强制刷新**——用户可能正在填表单或使用工具页。
- 推论：**对大陆用户，构建期快照往往不是兜底而是主要数据来源**，
  运行时刷新只在他们回源链路通畅时才生效。所以"隔多久重新构建并部署一次"
  是一个真实的运维参数，不是可有可无的优化。

## 二、数据流

- **服务端的数据库是唯一事实来源。** 仓库内的站点动态数据文件（`src/data/tools.json` 等）
  降级为**生成物**，由构建脚本从接口拉取覆盖，禁止手工编辑。
- **构建期拉取必须失败不阻断**：接口不可达时沿用上一次的文件并打 warning，
  构建以 0 退出。否则线上服务抖动会导致前端无法发布。
- 快照的字段形状与接口返回**逐字段一致**，因此前端只做整体替换、不做字段映射。
  形状不一致会直接表现为线上展示错误。
- 爬虫侧的数据滞后由定期重建解决，不为此引入 CI。
- 前端在**所有环境**都使用相对路径调用 `/api`（dev 由 Vite 反代、线上由 Nginx 反代），
  不引入 API base 环境变量。

## 三、Service Worker 的路径分流

`public/sw.js` 的 fetch 只按路径前缀分流，未匹配的同源 GET 全部落到
`staleWhileRevalidate`（缓存优先）。因此：

- `/api/`、`/uploads/` 必须在 `navigate` 分支之前 `return`（不调用 `respondWith`），
  交回浏览器走网络。实现见 `sw.js` 顶部的 `API_PATH` / `UPLOAD_PATH` 常量；
- **新增任何后端路径前缀，必须同步加进这条放行判断**；
- `/uploads/` 下的上传文件按内容哈希换名，否则同名换图会被长期缓存咬住
  （与 `/promo/` 目录当初的诉求相同）；
- **升 `CACHE_VERSION` 的时机**：仅在静态资源内容真正变化时升。
  只增改 SW 逻辑、不动资源时不必升——浏览器按字节差异更新 SW 脚本，
  无谓升版本会让全部用户重下资源。
- **破坏性接口变更必须搭 `CACHE_VERSION` 一起走**：导航是 StaleWhileRevalidate，
  回访用户当次运行的是上一版 JS，它调的是旧接口。不升版本，老壳子会一直用旧地址
  且用户没有任何提示。接口侧的完整约束见后端仓库 `docs/api.md` 的「接口演进」。

另外注意：SW 里 `return` 只跳过 Cache API，**浏览器 HTTP 缓存照常生效**。
读接口的缓存策略由契约规定，前端不要再叠一层。

## 四、站点动态数据只有一个入口

所有站点动态数据（卡片、父级菜单等）一律经 `src/composables/useSiteData.js` 获取，
**不得直接 import 数据文件**——运行时替换只覆盖这一个模块，
直接 import 的消费方会继续读到过期快照，且不会有任何报错。

所有**派生结果必须在调用时计算**。冻结在模块加载时的常量会失去更新能力：

- 站外域名白名单（`/embed/` 准入）必须每次调用时从当前数据派生，
  否则管理员新批的站外卡片其嵌入页会直接 404；
- 卡片是否在新标签页打开由数据字段 `openInNewTab` 驱动，不在组件里维护 id 列表。

选项式 API 组件注意读取时机：`render()` 内读取 ref 会被 Vue 追踪，
但在 `mounted()` 之类的方法里读取只是快照。数据刷新若发生在组件挂载之后，
这些组件需要显式重算。

## 五、只在构建时暴露的问题

`pnpm dev` 是纯 CSR，`vite-ssg build` 才有 SSR 阶段。以下问题在开发服务器上看不见：

- 组件必须在 `onMounted` 中请求接口，**禁止在 `setup` 顶层发起**——
  顶层调用在 dev 正常，构建时 SSR 会真发请求，甚至挂住预渲染；
- 构建期的快照脚本不能用相对路径（Node 侧无 origin），必须用带绝对 base 的 URL；
- `scripts/generate-seo.js` 的 `DISALLOW_PATHS` 必须包含 `/api/` 与 `/console/`。
  该列表同时决定 robots.txt 的 Disallow 与 sitemap 的排除项；
  公开站页面路径由 `scripts/route-list.js` 从路由配置自动扫出，不需要在此登记，
  而控制台的路由同样会被扫到，因此必须靠这个列表把它们排除出 sitemap。

## 六、开发环境矩阵

前端通过 `vite.config.js` 的 `server.proxy` 反代到本机后端。
`preview` 的 `host` / `port` / `proxy` 默认继承 `server`，配一处即覆盖两种模式。
后端在本机用原生虚拟环境运行，不用 Docker，以保留自动重载。

| 入口 | URL | SW 生效 | 可测移动端 | 生产产物 |
| --- | --- | :---: | :---: | :---: |
| V1 主力 | `http://192.168.0.66:5177` | 否（非安全上下文） | 是 | 否 |
| V2 | `http://localhost:5177` | 是 | 否 | 否 |
| V3 | `http://192.168.0.66:4173` | 否 | 是 | 是 |
| V4 | `http://localhost:4173` | 是 | 否 | 是 |
| V5 线上 | `https://tool.lonzov.top` | 是 | 是 | 是 |

> `preview` 默认端口是 4173：`--port 5177` 是 `dev` 命令的 CLI 参数，不写进配置，
> `preview` 不会继承它。

三类问题分别只在特定入口可见，**三类验证动作缺一不可**：

| 类别 | 典型问题 | 唯一可见入口 | 验证动作 |
| --- | --- | --- | --- |
| A 缓存层 | `/api` 被 SW 缓存优先命中、上传图换不掉 | V2 / V4 | `pnpm build && pnpm preview`，在 localhost 上确认数据即时 |
| B 局域网 | 写操作 403、Secure Cookie 导致登录静默失败 | V1 / V3 | 手机走局域网 IP **做一次真实写操作** |
| C 构建期 | 快照脚本失败、SSR 顶层请求、管理路由混入 sitemap | 仅构建 | 完整 `pnpm build`，检查预渲染产物与 sitemap |

主力入口 V1 结构性地看不见 A 类问题——`192.168.0.66` 是明文 http 非安全上下文，
Service Worker 根本不注册。因此接后端之后，**V4 必须成为例行验证入口**，
而不是「想起来才测 SW」。

### 联调时的后端配置要点

这三条是前后端衔接处最容易踩的，改任一端配置前先读：

- 反代会改写 Host，所以后端 `ALLOWED_HOSTS` 只需 `127.0.0.1`、`localhost`，
  不必跟着局域网地址变；
- `CSRF_TRUSTED_ORIGINS` 相反必须列全前端源：反代不改写 `Origin`，
  漏了局域网源会让手机端写操作 403，而 localhost 上测却是正常的；
- 联调环境 `SESSION_COOKIE_SECURE` / `CSRF_COOKIE_SECURE` 必须为 False：
  浏览器把 localhost 当可信源、允许在 http 下写 Secure Cookie，局域网明文地址不行。
  症状是「localhost 登录正常、局域网登录静默失败」。

### 控制台会话在前端侧的三条约束

后端契约见后端仓库 `docs/api.md`；这里只记前端必须怎么做：

1. **前端不保存任何令牌**。凭证是服务端下发的 HttpOnly Cookie，JS 读不到；
   本地只留账号名与角色用于展示，因此不存在"前端存密钥"的环节。
2. **写操作必须回填 `X-CSRFToken`**（取自 `csrftoken` Cookie）：Cookie 形态的凭证
   没有它就过不了后端的 double-submit 校验。统一走 `src/console/consoleAuth.js`
   的 `consoleFetch`，不要各自 `fetch`。
3. **会话有效性以服务端为准**：路由守卫只看本地痕迹，属于体验层；
   进入控制台由外壳调用 `GET /api/v1/console/me` 判定，过期或被吊销即回登录页。
   判断响应含义看响应体的 `code`，不要依赖 HTTP 状态码。

## 七、管理能力的边界

管理界面是**独立入口**，单独构建、单独部署，不进入公开站的运行时。
功能一律调后端 API，壳内不实现业务规则——写操作集中在后端才是唯一鉴权边界。

理由：公共组件是本仓库改动最频繁的部分。每多一个管理关注点，
之后每次改动公共 UI 都要带着它走，回归面会被永久放大。

## 八、第三方数据不直连

访问统计（Umami）与站点监控（Uptime Kuma）都由后端取数后下发：
统计走 `GET /api/v1/stats`，监控走 `GET /api/v1/console/uptime`。
前端不直连这两个第三方，原因是它们都在 Cloudflare 后面——

- 非浏览器 UA 会被下发 JS 质询（403 + `Just a moment…`），跨域也没有 CORS 头；
- API key 与状态页 slug 只能留在服务端，静态产物里放不住。

因此这两个面板读的都是自家接口，**取不到就留白**（统计沿用 localStorage 缓存），
不升级为页面错误态。新增同类外部数据源时按此处理，不要在前端直接 `fetch` 第三方域名。

## 九、人机验证的降级

极验仍是主验证；只有服务端判定极验网络异常 / 5xx 时，才返回
`403 captcha_fallback_required` 与一次性 `meta.fallback_token`。前端由
`TurnstileFallback.vue` 显式渲染 Cloudflare Turnstile，把 `turnstile_token` +
`fallback_token` 随原请求重发。**前端不得在未收到该错误时主动改用 Turnstile，
也不得把失败当成功**；Turnstile 失败或 `503 captcha_unavailable` 一律展示错误并停止提交。
字段与错误码正文见后端仓库 `docs/api.md`。
